PyRPL web GUI review — 2026-11-01

The reported problems are reproducible and systemic. Layouts frequently assume
that the browser width is also the panel width, that controls fit a fixed vertical
allocation, and that hiding overflow is an acceptable fallback. Those assumptions
fail in split panes, short windows, and narrow viewports. Increasing individual
selector widths alone would move the failures elsewhere.

This is an investigation and recommendation document. No GUI fixes were made and
nothing was deployed. Existing worktree changes were preserved. SHA-256 checks
confirmed that all 35 files in the pre-audit web source/test/config baseline were
unchanged. Only review artifacts and isolated audit scratch files were created.

Priority convention: P1 means misleading measurement display, hidden/overlapping

1. P1 — Scope time-axis labels can show the wrong numeric value.

The tick formatter removes trailing zeros even when they are part of an integer.
With zero decimal places: 50 becomes "5", 100 becomes "1", -50 becomes "-5", and
0 becomes an empty string. The resulting axis can read "-5 us, -25 us, us,
25 us, 5 us". This is a label-formatting defect; this review does not establish
incorrect samples or trigger positions.

Reproduction: the three-column Scope screenshot shows this pattern. Independently
evaluating the exact trimFixed function from the source confirms the substitutions.
The decimals calculation legitimately reaches zero for sufficiently large tick
steps; therefore the faulty formatter is used in normal plotting.
Source: web/src/scope-stream.ts:723 and :787.
Evidence: three-columns-scope.png; axis-format.json.
Direction: trim fractional padding only, preserve integer zeros and the zero label,
and test engineering-unit labels across positive, negative, and zero ticks.

2. P1 — ASG's fixed seven-column row makes selectors unusable and hides fields.

At 900×600, the two ASG cards remain side by side. Trigger/output selectors shrink
to roughly 34–35px, and fields at the right edge are clipped. Inside a roughly
416px split pane, the same row extends beyond its card. On a 390px viewport the

The outer grid allows 360px cards, but the inner row requires four columns of at

Source: web/src/main.ts:1169, :1192, :1861.
Evidence: medium-asg.png; phone-asg.png; three-columns-registers.png.
Direction: group ASG fields into meaningful rows that reflow to the card width;

Additional risks and checks to carry into implementation

- Many control labels are 10–11px and buttons are generally 24px high. This is
  dense for touch or magnified use. An 18px IIR marker and an 8px gutter warrant
  hit-area review. A 13px checkbox alone does not prove a target-size failure:
  its associated clickable label and spacing must be considered.
- --border is referenced by Configuration/IIR editor borders, but the main theme
  defines --panel-border. An unresolved custom property can invalidate the border
  declaration. Confirm the intended appearance when consolidating theme tokens.
- The debug footer properly stays at the bottom in the tested desktop case and
  is absent by default. At 1280×420 it consumes about 45px when enabled, further
  stressing the existing height constraints. Its 88px cap and scrolling are good
  safeguards, but long errors/mobile footer behavior still need dedicated tests.
- Network Analyzer and Curve Viewer skip resizing below small host dimensions.
  Test shrink-and-grow transitions, not only initial sizes, to ensure canvases,
  hit-testing, and saved scales recover together.
- Native dropdown popup behavior, focus-ring visibility, contrast, touch gesture
  conflicts, and actual 200%/400% browser zoom need manual cross-browser coverage.

Systematic prevention

These problems can be addressed with a small set of shared layout contracts and
tests. A new UI framework is not required, and a framework alone would not enforce
these contracts. The following is a proposed approach, not a patch plan already run.

A. Make panels responsive to their own width.

Establish inline-size containment on appropriate panel wrappers and use container
queries for their internal layouts. A 416px panel must choose the same readable
control arrangement whether it sits in a phone-sized window or a wide split
workspace. Use browser media queries for global chrome only where appropriate.
Do not indiscriminately apply size containment: block-size containment can interfere
with content-driven height. Use explicit height/scroll policies or ResizeObserver
where layout decisions truly depend on available height.
Reference: [MDN container queries](https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Containment/Container_queries).

B. Define reusable field and action-group components.

Each field type should have a readable minimum based on expected values, padding,
units, and native affordances. Grid column count should follow those minimums.
Allow outer containers to shrink with min-width:0, but do not let every inner
control shrink to nothing. Keep channel+visibility, read+address+length, write+
address+value, save/load/delete, and axis-navigation actions as explicit groups.
Wrap groups deliberately; make multiline buttons grow vertically if allowed.
Reference: [MDN min-width](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/min-width).

C. Give each constrained region an explicit overflow policy.

For every panel, specify which header stays visible, which form region scrolls,
which plot takes remaining space, and what happens below the useful minimum size.
Keep hidden overflow for intentional canvas/decoration clipping, not as the default
for forms. Avoid multiple accidental nested scroll regions. A scrollable child
cannot rescue controls clipped by a different ancestor or covered by another card.
Note that overflow:hidden may still scroll programmatically or on focus; that is
not an adequate substitute for discoverable pointer/keyboard access.
Reference: [MDN overflow](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/overflow).

D. Make the workspace honor panel requirements and provide a recovery path.

Current outer minimums of 220px horizontally and 140px vertically are unrelated to
each panel's inner requirements. Account for header, footer, gutters, control
height, and minimum useful plot area together. Clamp persisted proportions after
container changes. If all minimums cannot fit, offer a defined compact layout,
scrolling, sub-tabs, or expand-panel action rather than clipping. Reflow must not
unnecessarily reset the user's zoom, pan, cursor, focus, or edited field value.

E. Consolidate CSS ownership and design tokens.

The Network Analyzer/Housekeeping cascade conflict shows why a general late rule
must not silently redefine a panel's scrolling. Separate chrome, panel shell,
form/card, and plot responsibilities. Use scoped component selectors or deliberate
cascade layers, typed field variants, and shared sizing/spacing tokens. Document
intentional exceptions. Add static checks for undefined custom properties and
review broad selectors that change display, overflow, min-height, or grid tracks.

F. Treat plot labels and resizing as first-class GUI behavior.

Share tested numerical formatting, preserve zero/significant integer digits, and
budget tick density against the rendered label width. Test labels independently
from sample values. Provide usable chart minimums and explicit small-chart states.
Exercise repeated shrink/grow cycles while asserting zoom/pan and coordinate
mapping remain consistent. A canvas with painted pixels is not proof that its axes,
data, or controls are readable.

G. Add a reproducible responsive regression matrix.

Reuse the existing Playwright setup with deterministic fake data and isolated
workspace/configuration. Cover all 15 panels, tabs plus two/three-pane layouts,
widths on both sides of breakpoints, short heights, and actual browser zoom.
Include long selector values, names and paths; populated lists; errors/debug;
all tabs enabled; model/mode changes; reload; and drag-to-minimum transitions.

Assertions should verify:
  - each enabled control is visible or reachable through its designated scroll area;
  - control hit points belong to that control, not an overlapping sibling;
  - rows/cards do not overlap and group boundaries remain intact;
  - selected values/button labels fit their intended presentation;
  - no unexplained document-wide horizontal overflow;
  - menus/tabs/splitters remain usable with pointer and keyboard;
  - chart frames/axes remain useful and numerical labels are correct;
  - layout state and user plot view survive supported resize/reload transitions.

Current tests include useful label/control overlap checks at 1440×900 and
1024×768 and some mobile cases. Those checks do not systematically cover every
panel at narrow pane widths, ancestor clipping, control-to-control occlusion,
or selected-text fit. Extend that foundation rather than replacing it.

Use curated visual snapshots alongside geometry/interaction assertions. Stabilize
fonts/environment and volatile acquisition data; if waveform pixels are masked,
separately test chart drawing and dimensions. Screenshot-only tests cannot prove
scroll reachability or numeric correctness.
Reference: [Playwright visual comparisons](https://playwright.dev/docs/test-snapshots).

H. Include accessibility and manual review in the acceptance criteria.

Use named controls, visible focus, meaningful groups, and keyboard-operable
splitters. Review effective pointer targets including labels and spacing.
Automated accessibility checks are useful but do not replace keyboard, zoom,
screen-reader, and real-device review.
References: [WAI window splitter pattern](https://www.w3.org/WAI/ARIA/apg/patterns/windowsplitter/),
[WCAG target size guidance](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html),
[Playwright accessibility testing](https://playwright.dev/docs/accessibility-testing).

Use reflow testing at 320 CSS pixels as a practical acceptance target for ordinary
controls. Plots may legitimately need two-dimensional viewing; that does not
justify losing surrounding form controls. Test real zoom separately from viewport
emulation because they are not identical environments.
Reference: [WCAG reflow guidance](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html).
